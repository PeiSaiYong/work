Minmed Digital Name Cards

A centrally managed digital name card, like Zapkad's company plan. Admins create and change every card. Staff never sign in. Anyone with a card's link can open it, but nobody can find it on Google.

Based on Technical Specification draft 0.2 (15/10/2026), your decisions on 16/10/2026, and the features Zapkad lists publicly. Draft, 16/10/2026.

Links and privacy

  • Link format: me.minmed.sg/card/{FirstLast}/{code}, for example me.minmed.sg/card/AlexTan/AlTa-x7K2p9Qe. The code is random, at least 10 letters and numbers, made by the server and never reused. The /card/ prefix, like Zapkad's /biz-card/, keeps clear of Base44's own addresses.
  • The name part is only for people: the server finds the card by its code alone. If someone's name changes, old links and printed QR codes keep working.
  • Every public address uses the same random code: the card page, contact file, card image and Wallet pass. Never a counting number.
  • Hidden from Google, twice over: no list of cards anywhere (no sitemap entries, no staff directory, the home address redirects to minmed.sg), and every card page, image and contact file tells search engines not to index it. On Base44 that means the card page's "Search visibility" switch plus a noindex header on files from backend functions, checked after every publish. Don't block card addresses in robots.txt: Google then can't see the "don't index" instruction and may still list a link someone posted elsewhere.
  • If a link is misused: a Super admin issues a new code. The old link then shows "No card found".
  • No CAPTCHA in the first version: random codes stop anyone collecting cards by guessing names, which was the main reason for the CAPTCHA rules in spec 0.2. Normal platform rate limits still apply.

Two lessons from Zapkad's public card page

Its card pages don't tell Google "don't index". Zapkad relies on never listing cards anywhere. If someone posts a card link on a public website, Google can still pick it up. Minmed should do both.

Its Save to Phone link uses a disguised counting number. Your example card's contact file is at /save-contact/MTY5OTM5, which decodes to 169939, not the random code. That pattern could let someone download other people's contact files by counting. I didn't test it. Minmed's contact files must use the random code.

Test before the build (throwaway app on a test subdomain)

  1. Open a card link as WhatsApp and as Google's crawler. Check the preview tags, the noindex instruction and the sitemap, then share the link in a real WhatsApp chat.
  2. Download a contact file and a Wallet pass from a backend function in iPhone Safari, Android Chrome, WhatsApp and Gmail.
  3. Create an Apple pass and a Google Wallet save link inside a backend function.
  4. Check that a non-minmed Google account is refused, an Admin can't make themselves Super admin, and an anonymous visitor can't list cards.
  5. Check that emails reach staff and manage@minmed.sg, and that a scheduled job runs.

Accounts and costs to arrange

  • A verified email sending domain, set up by IT.
  • Apple Developer Program, US$99 a year, using Minmed's D-U-N-S number.
  • Google Wallet issuer account with a business profile (free, needs Google's approval).
  • Option C only: hosting for the public card pages.

Patterns this scope copies

  • No staff logins, Wallet pass by email (Uniqode, Mobilo): the card email with Wallet buttons.
  • Deactivate and keep the record (Blinq): a rehired person gets their old card back.
  • Stable link and QR code, live content (Blinq, Uniqode): edits never break shared links or printed QR codes.
  • Spreadsheet import (four of five): for loading every staff member at launch.
  • Our own page for a departed card: no platform documents what visitors see, so the scope defines it.
  • An activity log and "don't index": platforms barely document them, so the scope makes both explicit requirements.

Patterns left for later

  • Admins limited to one department or clinic (Popl, Mobilo, HiHello).
  • A read-only Viewer role, for example for management (Uniqode).
  • Directory sync that switches cards off automatically when someone leaves (all five).
  • A no-login link where staff request changes for approval (Uniqode, Popl). For now, staff reply to their card email.

Sources: vendor help centres, including Blinq admin onboarding, HiHello roles, Popl roles, Uniqode Wallet passes and Mobilo admin features.
