Gateway and error messages

Is there a "gateway error"?

Not as such. The spec has no message called a gateway error, and the gateway itself is Pending: the spec says the CAPTCHA provider, the gateway design and how they're deployed are still to decide.

One fact shapes that decision: Base44 requires DNS-only records, so Cloudflare's firewall isn't automatically in front of the app. Protection has to be added on purpose, and the Base44 and origin APIs need it too, not only the public address.

These are the error-type messages the spec does define:

MessageWhen it appearsWording status
Temporary verification errorThe live check fails, for example during an outage.Heading defined. Explanation text not defined.
Retry or status-unavailable messageThe CAPTCHA check or the card lookup fails.Not defined.
CAPTCHA checkBrowsing looks automated, for example many different cards very quickly.Not defined (§8).
Slowed down or blocked for a whileRepeated suspicious activity.Wording and duration not defined (§8).
"No card found at this address. Check the link or visit minmed.sg."The link doesn't exist, or the card isn't approved yet.Defined.

§7.1

Someone pretends to be a Minmed staff member

What happens

  • An impersonator forwards a genuine card link or makes a fake card.
  • A genuine link still shows the real officer's details and official contacts.

How we reduce it

  • Before approval, the server checks the officer's company Google account against the staff directory.
  • The live page shows official contact details on the Minmed domain.
  • The How to verify panel Proposed tells recipients to confirm sensitive requests through a contact they already know.

What we can't prevent

  • Anyone can forward a genuine link. Active confirms the card, not the sender.

§7.2

A copied card is altered

What happens

  • When the recipient opens the link, the live page shows the real approved details, and the difference is visible.

How we reduce it

  • The link carries only a card ID, never the editable title or number.
  • Every opening triggers a live lookup.
  • The official URL and QR are on the card, and the tick appears only on the live page.

What we can't prevent

  • A genuine QR can be pasted onto an altered image. It only helps if the recipient opens the link and compares.

§7.4

A staff member leaves

What happens

  • The live link shows Card unavailable and the departure notice.
  • The officer can no longer share the card.

How we reduce it

  • Deactivation is immediate and central.
  • New contact and card downloads stop, new WhatsApp preview images are refused, controlled caches are cleared Proposed.
  • Every download re-checks status.
  • manage@minmed.sg is notified and an audit record is kept.

What we can't prevent

  • Old WhatsApp messages, saved images and saved contacts can't be erased remotely.
  • Who triggers offboarding and how quickly: Pending

§7.5

A staff member publishes unauthorised or wrong details

What happens

  • The change stays pending and is not public until approved.

How we reduce it

  • Name, designation and contact changes need approval.
  • The server checks ownership and reviewer permissions.
  • Approval applies only to the exact version reviewed, and editing during review restarts it.
  • Pending edits are never public.

What we can't prevent

  • Whether photo, biography, languages and LinkedIn changes need approval: Pending. Proposed: review all public changes.

§7.6

Someone edits another officer's card, or signs in with a non-Minmed account

What happens

  • The request is refused.

How we reduce it

  • Identity, directory match and ownership are checked on the server for every request, not only by hiding buttons.
  • A typed email address is never accepted as proof.

Why hiding buttons isn't enough

Anyone can send a request without using the app's buttons. So identity, directory match and ownership are checked on the server for every request.

§7.7

Bots harvesting the staff list or guessing names

What happens

  • Ordinary visitors pass straight through.
  • Suspicious traffic gets a CAPTCHA.
  • Repeated abuse is throttled or blocked for a cooldown period.

How we reduce it

  • No public staff list or bulk endpoint.
  • The server counts every profile-data and download request.
  • Each request is assessed on per-session limits, IP activity, how many different cards are requested and failed challenges.
  • Limits still apply after a CAPTCHA pass.
  • Unapproved cards return the same not-found response as links that don't exist.

What we can't prevent

  • The WhatsApp preview is public by design and can be read by scrapers.
  • CAPTCHA-solving services and slow, spread-out scraping can still copy public details. No promise of zero scraping.
  • Thresholds, time windows and cooldowns: Pending

§7.8

Attempts to get around the checks

What happens

  • Reused tokens, direct API calls and fake crawler identities are rejected, or the user gets a retry message.
  • No protected data is released.

How we reduce it

  • Candidate Cloudflare Turnstile, validated on the server. Tokens are single-use, expire after five minutes, and are checked against the expected hostname and action.
  • Invalid, expired and reused tokens are rejected.
  • The Base44 and origin APIs are protected as well as the public domain.
  • Client IP information is trusted only from the chosen gateway.
  • A User-Agent claiming to be a trusted crawler is not taken as proof.

What we can't prevent

  • Base44 requires DNS-only records, so Cloudflare's firewall isn't automatically in front of the app.
  • CAPTCHA provider, gateway design and deployment: Pending

Try it: how the server treats a CAPTCHA token

When someone passes a challenge, their browser gets a token to send with the next request. Using the spec's Candidate Cloudflare Turnstile, the server checks that the token is valid, single-use, under five minutes old and issued for the expected hostname and action.

§7.9

Genuine visitors on shared office Wi-Fi get challenged

What happens

  • Several real people behind one IP could trigger checks.

How we reduce it

  • Per-session limits are preferred over IP-only rules. IP is one signal, not a person.
  • The first response is a challenge, not a block.
  • Shared-network complaints are tracked before thresholds are set.

What we can't prevent

  • Some friction is possible until thresholds are tuned.
If the rule counted only by IP address Not preferred
ABCDE

Five colleagues on the same office Wi-Fi each open one different card. To the server that's one IP address opening five different cards in a minute, which could look like scraping.

Counting per session, with IP as one signal Preferred
ABCDE

Each person has their own session that opened one card. Nobody looks automated. IP activity still counts, but as one signal, not as a person.

If someone is caught anyway, the first response is a challenge, not a block. Shared-network complaints are tracked before thresholds are set.

§7.10

Private information leaks

What happens

  • Only approved public fields are ever returned to the public.

How we reduce it

  • An explicit list of public fields.
  • The website, WhatsApp preview, contact file and card image are all generated from the same approved version.
  • A withheld mobile is absent from every output, its metadata and its image files.
  • The server filters fields, and a launch check confirms this.

§7.11

Profiles appear in search results

How we reduce it

  • Each page is set to noindex and excluded from the sitemap.
  • Every staff page, image and alternate address is checked before launch.

What we can't prevent

  • This is an instruction to search engines, not access control or protection from scraping.

What's done

  • Each staff page is set to noindex.
  • Staff pages are left out of the sitemap.
  • Every staff page, image and alternate address is checked before launch.

What it isn't

  • noindex is an instruction to search engines. Well-behaved ones follow it.
  • It isn't access control: anyone with the link can still open the page.
  • It doesn't stop scraping. That's what the measures in §7.7 are for.
§7.12

What happens

  • Recipients see a temporary verification error.

How we reduce it

  • The page never shows a fresh Active result or claims the person has left when the check fails.
  • No protected response is released.

§7.13

An outdated WhatsApp preview after an update or departure

What happens

  • Old messages may still show old details.

How we reduce it

  • The preview never claims to be verified.
  • It says "Open link for current details." Proposed
  • The preview image updates on approval.
  • New images are refused after deactivation.

What we can't prevent

  • Previously sent messages and third-party caches may keep the old image.
  1. Day 1. Officer shares the link. WhatsApp stores a preview snapshot.
  2. Day 10. A change is approved. The preview image updates, so new shares show the new details. The Day 1 message still shows the old snapshot.
  3. Day 40. Officer leaves. New preview images are refused Proposed. Old messages still show the Day 1 snapshot.
  4. Any day. Tapping the link opens the live page, which always shows the current state.

§7.14

Administrator misuse or mistakes

How we reduce it

  • Deactivations and administrator edits are emailed to manage@minmed.sg with the responsible account, the card and the time.
  • An audit record is kept.
  • An email failure never reverses a saved approval or deactivation.

What we can't prevent

  • Extra reviewers, and whether administrator edits need independent approval: Pending

Copies can be shared after the person has left, and they'd still look valid. That's why only the live page ever carries a tick.

The page never uses the word "Verified", so it doesn't suggest the sender's identity has been checked.

Ways to check a card is genuine

  1. Address bar reads exactly me.minmed.sg.
  2. Status shows ✓ Active staff profile with a check time from when you opened the page.
  3. Details match what you were given. If they differ, trust the live page.
  4. How to verify panel (Proposed) lists these checks.
  5. Open it yourself: tap the link or scan the QR rather than trusting an image.
  6. Sensitive requests: confirm through a Minmed contact you already know.

Not proof on their own

  • The WhatsApp preview
  • A screenshot
  • A downloaded card image
  • A saved contact
  • A QR code
  • A page that looks like Minmed's

Pending: signed links, and watermark, reference or date labels on downloads.
